# <img src="assets/icon.svg" width="28" height="28" alt="" /> dsh-customer-service-plugin

一个可以装进任意 DeepSeek Harness 实例的**客服插件**：在 DSH 里提供一个**纯点击操作**的中文客服控制台，不需要会 AI 也能用。

它做四件事：

1. **一键巡逻（v0.3.0 新增）** —— 点一次按钮，依次打开账号下**该渠道的全部店铺**
   （Amazon 的「买家与卖家消息服务 · 需要回复」/ TikTok Shop 的客服会话 / 沃尔玛的 Customer
   收件箱 / SHEIN 的 chat工作台 / TEMU 的卖家后台），读会话、按意图套模板生成草稿，落进草稿库与工单队列，
   并**默认直接填进紫鸟浏览器里那条会话的回复框**（v0.5.0 起；无头模式已移除）。
   全程**只读页面 + 只填不发送**。
2. **调整客服计划** —— 回复规则与话术模板、排班分工、待回复队列（工单池）、生成计划（空闲时段批量预生成草稿）。
3. **通过紫鸟CLI 操作店铺** —— TikTok Shop / Walmart / Amazon / SHEIN / TEMU 的买家消息、订单与物流查询、评价回复、售后与退款工单。
4. **通过飞书CLI 回复客服邮件** —— 收件、生成草稿、人工点「发送」才真正发出。

**贯穿始终的一条硬规则：草稿先行。** 插件自己只生成草稿，任何渠道真正发出都必须由人在界面上点一次「发送」。


---

## 一键巡逻（v0.3.0 / v0.4.0 增加飞书邮箱 / v0.5.0 默认填入回复框并移除无头）

控制台 → **工作台 · 巡逻** → 一个大按钮：

> 一键巡逻：全部 Amazon 店铺（N 家）

点下去之后，服务端按顺序做这些事（**串行**，一次只开一家店的浏览器）：

```
store list                       → 过滤出 platformName 含「亚马逊 / Amazon」的店铺
                                   （这一步也可以由界面上渠道右侧的按钮手动触发）
  for 每家店：
    store open --id <storeId>    → 打开（已开则复用）
    page visit  收件箱 ?fi=responseNeeded
    page exec   读 .case-list-items 里的会话（买家 / 主题 / 订单号 / 到期）
    for 前 N 条会话（默认 50，即上限）：
      page exec  第 i 行滚进可视区 + el.click()  → 打开会话
                 （不用 page click：实测它会「鼠标指令已发送、DOM click 事件未观察到」）
      page exec  读整段对话
      buildDraft 判意图 + 套模板  → 生成英文草稿
      写入草稿库 drafts/drafts.json（同 caseId 去重）
      写入工单队列 queue.json（channel=amazon，状态 drafted）
```

### 每个渠道右边的两个按钮

店铺列表带 **60 秒缓存**（`store list` 要一两秒，控制台刷新又很频繁），而且**在紫鸟里
新增店铺不会通知 DSH**。所以每个渠道那一栏右侧有两个按钮，分工完全不同：

**「仅刷新列表」** —— 只重跑一次 `store list`（`POST /cs/api/patrol/scan`）：不生成草稿、
不打开浏览器，紫鸟里加/删了店铺时用它最快。

- 回来后直接告诉你**变了什么**：「共 71 家店铺，其中亚马逊 8 家；新增：Amazon-XXX」，
  新店铺自动勾上、消失的自动从勾选里去掉，列表里新店会带一个「新」徽标；
- 账号下的非亚马逊店铺（实机上是 71 − 8 = 63 家）折叠在「另有 N 家非亚马逊店铺」里，
  带着平台名和原因 —— 这样「某家店为什么没被巡逻」有一句明确答案，而不是让人怀疑漏扫。

### 店名带「停用」的店自动排除

紫鸟的 `store list` **没有状态字段**（每条只有 `storeId` / `storeName` / `platformName` / `ip`，
2026-10-10 实测），所以「这家店停了没」只能看**店名** —— 而运营本来就是用店名标注的
（实机：`Walmart-Yanosaku-已停用`、`Cdiscount-停用`、`敦煌网-停用-管理员`、`Temu-JDDX停用-管理员`）。
判据是 `停用 / 废弃 / 作废 / 弃用 / 注销 / 下线 / disabled / retired / deactivated`，命中之后：

- **不进巡逻目标**：不会为它开一次浏览器（打开只会撞登录页或错误页，白跑一趟还留一条看不懂的失败）；
- **不混进「该平台暂未接入」**：那是另一回事 —— 混在一起会让人以为这个平台没接好，而实际上是店自己停了；
- 在每个渠道块里**单独一栏**「已停用的店铺 N 家（不巡逻）」列出店名与平台名，跳过谁一眼可见。

要恢复巡逻，把店名里的停用字样去掉即可（**刻意不认**「未启用 / 注册中」—— 那些是等着接入的新店，
藏掉它们就成了真的漏扫）。三个店铺渠道（Amazon / TikTok / 沃尔玛）共用同一条判定，
实现在 `lib/ziniao.js` 的 `isRetiredStore`，规范化店铺列表时一次算好。

**「重新扫描」** —— 真干活的那个：只巡逻**这一个渠道**，走完整链路（扫描 → 逐店读取 →
生成草稿 → 写进紫鸟浏览器的回复框）。和顶部「一键巡逻」是同一套代码，只是把范围限定在
这个渠道、把目标限定在当前勾选上。

- **跑完不关闭浏览器**：这个动作强制 `closeAfter: false`，**不看**界面上「跑完关闭店铺」
  那个勾选。草稿正躺在回复框里等人核对，跑完就把窗口关掉等于白填一场。
- 勾选是**按渠道**算的：只勾了亚马逊的店，再去点飞书邮箱的「重新扫描」，邮箱不会因为
  「一个都没勾中」而空跑 —— 该渠道全勾或全不勾都按「这个渠道全部目标」处理。
- 渠道未启用时按钮是禁用的，鼠标悬停会说明原因。

两个刻意的行为（两个按钮都适用）：

1. **扫描失败不清空列表**：紫鸟偶发未登录/连不上时，保留上一次成功的结果并附上错误，
   否则你分不清「真的没有店铺」和「这次没读到」。
2. **首次扫描不报「新增」**：没有基准就没有差异，报出来只会是假信号。

### 只显示这个账号真有店铺的渠道（v0.15.0）

渠道清单是插件**写死**的（亚马逊 / TikTok / 沃尔玛 / SHEIN / TEMU），而紫鸟 `store list`
只返回**这个账号被授权**的店铺 —— 公司里每个人能看到的店不一样。所以巡逻页会按**当前扫描
结果**把「本账号一家店都没有」的渠道收起来，并用一行提示 + 一个「显示这些渠道」按钮兜底：

| 账号 | 巡逻页画出的平台块 | 收起（可一键显示） |
|---|---|---|
| 8 亚马逊 / 2 TikTok / 2 沃尔玛 / 1 SHEIN / 9 TEMU | 全部六块 | — |
| 只有 3 亚马逊 / 2 TikTok | 亚马逊、TikTok、飞书邮箱 | 沃尔玛、SHEIN、TEMU |
| 只有 1 家沃尔玛店 | 沃尔玛、飞书邮箱 | 亚马逊、TikTok、SHEIN、TEMU |

判据只用两个数：`scan.total`（**全账号**店铺数 —— 各渠道拿到的都是同一份）与
`scan.items`（本渠道可用目标数，已排除停用店）。**五条刻意不收起**的例外：

1. **邮箱渠道**（`kind !== 'store'`）：它没有「店铺」这个概念，能不能用由邮箱配置决定；
2. **已停用的渠道**（渠道开关关着）：那块里挂着渠道自己的启停开关，收起就再也打不开；
3. **这次扫描失败 / 未启用**：**不知道**到底有没有店，不许猜；
4. **全账号一家店都没扫到**（`total === 0`）：多半是 CLI 或登录的问题，全收起会让整页空掉；
5. **有停用店**：0 家可用是因为店都停了，那一栏正是要给人看的解释。

- 收起只是**显示**层的动作，**不影响巡逻目标**：跑哪些店由各渠道块里的勾选与渠道开关决定，
  不会因为「界面上看不见」就少扫一家店。
- 在紫鸟里加了新店，点一次「仅刷新列表」，对应渠道**自己就会回来** —— 渠道不会因为
  「这个账号没店」而变得不可达。
- 这个偏好存在**浏览器本地**（`localStorage` 的 `cs.patrol.showEmptyChannels`），**不进**
  `settings.json`：它是每个操作员自己的查看偏好，写进设置就变成「我把别人的界面改了」。
- 判定抽成纯函数 `channelsWithoutStores`（`assets/js/platform-summary.js`），
  用例在 `test/platform-summary.test.js`，页面接线锁在 `test/assets.test.js`。

### 定时巡检（**每个平台一份**；v0.5.0 新增，v0.11.0 从「一张全局表」下沉到各平台）

**工作台 · 巡逻** 页里，**每个平台块底下**都有一块属于它自己的「定时巡检」：

```
▾ 亚马逊（8）                        [登录全部未登录的店] [仅刷新列表] [重新扫描]
  ☑ Amazon-Cozynome-管理员   ☐ Amazon-FUSOU-客服   …

  ┌ 定时巡检  已启用 ───────────────────────────────────────────┐
  │ ☑ 启用亚马逊的定时巡检                                       │
  │ 巡检时刻（每天各跑一次，共 3 次；上一轮没跑完就跳过，不会并发）│
  │ [09:00] 删除   [14:00] 删除   [20:00] 删除                    │
  │ ▸ 巡检店铺：全部 8 个目标                                     │
  │ [+ 添加一次巡检]   [保存亚马逊的计划]                         │
  │ 已启用 · 今天 3 个时刻，已跑 1 次 · 下次 14:00（10-10 14:00） │
  └──────────────────────────────────────────────────────────────┘
```

**为什么按平台拆开**：三个平台的班次根本不同（亚马逊 US 店盯得最紧、沃尔玛只有两家店、
邮箱一天看一次就够）。一张全局时刻表要么让所有平台陪跑，要么逼人把整个功能关掉。
**巡检店铺也各设各的**：亚马逊只巡客服主号、把不归客服管的店排除掉，不该顺手把别的平台
也限成同一批 id。

| 设置 | 默认 | 说明 |
|---|---|---|
| 启用 | **关闭** | 无人值守会自己打开店铺浏览器，必须由人显式打开 |
| 巡检时刻 | 09:00 / 14:00 / 20:00 | 一天三次；点「+ 添加一次巡检」加，点「删除」去掉 |
| 巡检店铺 | 全部 | 点开「巡检店铺」逐店勾选；**一个都不勾 = 全部**（与手动巡逻的勾选口径一致） |

- **每个平台各存各的**：时刻与店铺写进 `settings.autoPatrol.channels[渠道 id]`，保存只提交当前这个平台，
  不会顺手改到别的平台。**改完记得点这块面板里的「保存…的计划」** —— 它是本地编辑，不点保存不生效。
- **没单独设置过的平台沿用「全局默认计划」**（`settings.autoPatrol.enabled` / `.times`，面板上会标一个
  「沿用全局默认」角标）。这一层是从 v0.10 那张全局时刻表**原样继承**下来的：升级不改变行为，
  谁要单独改，在自己的面板里保存一次即可。
- 到点跑的是**这个平台的完整巡逻**：扫描 → 读会话 → 生成草稿 → 填入回复框，和人工点「重新扫描」
  是同一套代码，只是发起者从人换成了一颗每分钟看一眼的心跳。
- 时刻表可以随便加减（去重、按时间升序，最多 48 次）。**存的是「每天几点」，不是「隔多久」**：
  所以不会出现「重启之后从头再数一个间隔」这种事。
- 按 settings.timezone 判时刻，不看宿主进程的本地时区。
- **一个平台的一个时刻，一天只跑一次**：跑过的时刻按「日期 + 时刻 + 平台」记账，重启 DSH 也不会重复补跑。
- **到点后的宽限 5 分钟**：心跳可能被卡住、机器可能休眠、DSH 可能刚好在 09:00:40 重启 ——
  只认「正好这一分钟」会静默漏掉整次巡检，所以 09:00 的巡检在 09:05 之前发现都算数。
- **永不并发**：上一次巡逻还在跑，这一拍到点的就跳过（审计里记一条 auto-skip，带平台名）—— 而且这一次
  算用掉了，不补跑、不堆积。**同一拍到点的平台合并成一次巡逻**：它们本来也只能串行跑，合成一次
  还省得第二个平台被「忙」白白挤掉。**永不关浏览器**：自动跑同样强制 closeAfter: false。
- 每店条数 / 最多几家**沿用巡逻设置**，自动跑不该有另一套悄悄生效的参数。
- 渠道本身没启用（比如飞书邮箱渠道关着）时面板上直接标「该渠道未启用」：开关和时刻都还在，但一步都不会跑。
- 记账落在 run/auto-patrol.json；每次启动在活动审计里记一条 kind=patrol / name=auto-start
  （带 runId、平台清单、各平台的时刻、晚了几分钟），启动失败记一条 ok:false —— 而且因为「先记账再启动」，
  失败不会变成每分钟重试的热循环。
- 工作台的大按钮下面有一行**总状态**（哪些平台开着、下次是哪个平台几点）；每个平台块底下那一行
  再说这个平台自己的细节：今天跑了几次、当前为什么不跑、上次自动跑的结果与新草稿数。

### 校准过程中撞出来的四个坑

1. **会话行不能用 `:nth-of-type(N)` 定位。** 行是 `<div>`，该伪类按**同类型兄弟**计数，
   而卡片之间夹着虚拟滚动占位元素，于是 `nth-of-type(2)` 根本不是第 2 行 ——
   实测表现是巡逻报「第 2 条会话不在列表里了」并**静默跳过那一条**。
   改成按**数组下标**取（`clickScriptByIndex`），与列表解析给出的 index 严格同源。
2. **消息方向不能靠几何或类名判断。** 实机 21 条消息的 x 坐标**全是 488**，
   类名差异也不稳定（试过靠父级类名判定，误判率很高）。可靠判据只有**发送者前缀**：
   我方消息带客服名（`Customer Service-RUI`）或店铺名（`FUSOU Furniture`），买家消息不带；
   另有一类系统消息（「会话被分配…」/「系统关闭聊天」）**两边都不算**。
3. **本平台没有会话级深链。** 在 /chat 里点不同会话，`location.href` 恒为 `/chat/inbox/current`；
   会话卡片的 id 是 `chat-room-conversation-list-item-0` 这种**位置序号**，不是稳定标识
   （列表一刷新就指错会话）。所以 `conversationUrl()` **永远返回空串**，界面据此隐藏「打开原会话」。
   恒返回空串（而不是退回消息中心首页）是刻意的：一个能点开、看着像对的错链接，比没有链接糟得多。
   对应地，人工点「填入回复框」时填的是**当前打开的那个会话**，返回值里带 `located: false` 明说这一点。
4. **回复框是常驻展开的**，不需要点任何「展开回复框」按钮（那个常量实测为空数组）。

| 登录 | ✅ **自动登录** | 只点「登录 / 继续」；账号密码与 2 步验证码都由紫鸟自己填，插件不接触凭据 |
| 会话级深链 | ❌ **实测不存在** | 点开不同会话，地址恒为 `/seller-communication/Customer?start=1`，`conversationUrl()` 恒返回空串 |

登录判据是**实测的**：未登录时入口 302 到
`https://login.account.wal-mart.com/authorize?...&clientType=seller&redirectUri=...`，
所以「这家店没登录」和「页面改版了」在结果里分得开 —— 前者会被巡逻**跳过**（不算失败），
后者才会记成这家店失败并带上试过的选择器。

#### 校准中撞出来的两个坑（都是真事故级）

1. **裸 `.message` 是「列表行」的类名，不是消息元素。** 列表行是 `.message.p-16`（实机 25 个），
   所以消息元素的兜底里一旦放裸 `.message`，25 条列表行就会被当成会话正文 —— 巡逻会拿着一堆
   列表摘要去判意图、生成草稿，而且**不报任何错**。第一版兜底就是这么写的，实机一测才发现。
2. **裸 `textarea` 会命中沃尔玛 Marty AI 助手的输入框。** 页面上共有 3 个 textarea：真回复框、
   浏览器插件的 1x1 框（`#dxmCopyUrl`）、AI 助手的 `.chat-input-textarea`。退回裸 `textarea`
   就等于把客服草稿**打进 AI 对话框**。而真回复框**根本没有 placeholder 属性**
   （那句「在此处输入回复」是旁边的一个 `<label>`），所以第一版按 placeholder 找它的兜底命中 0。

两条都落成了回归锁测试（`test/walmart.test.js` 里的「消息选择器里不许有裸 .message，回复框候选里
不许有裸 textarea」），并且剧本与代码的选择器是**逐字对照**的（少一个字符就挂）。

**尚未覆盖**（写在适配器的 `calibrationNote` 与剧本的 `calibration.pending` 里）：
列表容器是 CSR 哈希类名（`Hiyc8`），随构建变 —— 所以列表脚本**不强依赖容器**，直接找行；
系统通知类消息目前与买家消息一样按「非我方」处理；附件、模板下拉、改单等交互未涉及；
右侧的**消费者 + 订单详情**面板（金额 / 承运人 / 追踪号 / SKU / 买家地址）只在部分店出现，
结构已校准但**尚未接入提取**（接入时必须 best-effort —— 两店布局实测不同）。


命中 1 个以上的候选就该被提到候选数组第一位，然后同步更新 `lib/platforms/walmart.js` 与
`assets/playbooks/walmart.message.json`（两者的选择器由测试逐字对照，改一处必须改另一处）。

**三条与其它平台不同的口径：**

1. **退货/退款模板「只承接、不断言」。** 面单、承运商、退货仓、退款金额与到账都不是客服一个人
   能定的；9/30 实机上就有一单是这样升级成纠纷的（买家连问三次退货面单，卖家三次答非所问）。
   所以 refund / return 的草稿里**不写**「已为你办理」「X 个工作日到账」，只确认诉求、说明正在核实、
   承诺回到这个会话里给结论 —— 并且强制挂一条人工核实提示（`notes` 里能直接看到）。
2. **订单号只认高置信形态。** 15 位 20 开头（实机 `200015455387691`）、13 位 20 开头、以及带
   order / 采购订单 标签的 15 位裸串。亚马逊 3-7-7 与 TikTok 的 16 位串**一律不认** ——
   认错单号发出去不可逆，认不出只是人工补 5 秒。
3. **损坏走「补发配件」口径**（与全部渠道一致）：直接向买家要损坏部位的照片，并承诺免费补发

   索要订单号**（会话里已经有这一单，再问一遍只是多一轮往返）。

⛔ 和前三个渠道一样：**巡逻链路上不存在发送动作**。草稿只进插件草稿库，人工点「填入沃尔玛回复框」
时只往回复框写文本（沃尔玛没有会话级深链，填的是**当前打开**的那条会话，返回值里 `located:false`
明说这一点），发送必须由人在沃尔玛页面上点「发送回复」。

#### 「登录」按钮会顺手把登录页切到「手机号登录」

跨境卖家中心的登录页默认停在**扫码登录**（实测 React 里是
`useState(sessionType === Normal ? Scan : Account)`，扫码在前），而客服日常走的是手机号那一栏。
所以 TEMU 渠道的「登录」按钮比别的渠道**多做一步**：开店铺 → 导航到后台 → **点一下「手机号登录」
那个 tab**（`PHONE_TAB_SCRIPT`，用 `el.click()`；2026-10-12 实测切成功并回读 `active=手机号登录`）。

**这一步仍然没有越过「插件不代替人登录」的线**：只切 tab，不填任何内容、不点「登录」、不碰验证码、
不处理滑块 —— 凭据与验证码还是只能由人自己来。切 tab 的结果会跟着接口回去（`phoneLoginTab`），
界面上直接用一句话说出来；没切成功也照实说「登录页默认停在扫码登录，请手动点一下那个 tab」。
美区 Seller Central 的登录页只有 Sign in / Sign up（实测），这个后台**不做**这一步

   候选地址再看一次）；`--open` 则与点「登录」同一套代码（含切 tab）；
3. 把实测到的会话行 / 正文选择器填进 `ROW_SELECTORS` / `THREAD_SELECTORS`，把
   `CONVERSATION_WORKBENCH_URL` 填上，把 `verified` 改成 true，并在 `calibrationNote` 里写清
   校准现场（店铺 + 会话 ID）。

### 登录：巡逻之前的一步（v0.8.0）

店铺平台大多要先登录才能巡逻，但**两条线的处理不同**：

| 渠道 | 未登录时巡逻怎么做 |
|---|---|
| **沃尔玛** | **自动登录**：登录页的账号密码由紫鸟密码管理填好、2 步验证码由紫鸟验证码服务自动填入，插件只点一下「登录 / 继续」，然后照常巡逻 —— 无人值守 |
| TikTok Shop | 跳过这家店（`未登录，请先点「登录」`），等人手动登录 —— TikTok 的登录有滑块/邮箱验证码，插件不代劳 |

自动登录的边界（写死在 `lib/platforms/walmart.js` 并被测试逐条钉住）：**只点文案精确等于「登录 / 继续」的按钮，没有任何输入动作** ——
不代填账号密码、不碰验证码；2 步验证页在验证码为空时不点「继续」，只等紫鸟把码填进来，等不到就如实报「需要人工一次」。
巡逻结果里会单独记 `sourcesAutoLoggedIn`，界面选项行可以关掉它（「未登录时自动登录」）。

**自动登录的渠道在界面上不暴露登录状态**（和亚马逊那块一样）：没有状态点、没有「N 家未登录」角标、
没有「登录」按钮、也没有「巡逻会跳过它们」的横幅 —— 把「未登录」摆在人面前，只会让人以为要自己动手，
而实际上巡逻会自己处理完。自动登录真失败了也不靠红点，而是写在巡逻结果的 `auth.autoLogin` 里
（哪一步、点了几次、卡在哪），再落到这条结果的 `note` 上。

人工入口并没有关：显式调 `POST /patrol/login` 带 `channel` + `storeId` 仍然能把登录页开出来等人 ——
只是界面上不再为这类渠道画按钮。

相应地，巡逻页每个**需要人工**登录的店铺行都有「登录」按钮与状态点（沃尔玛不在此列，它自己会登）：

    [店铺名]  ●已登录        [登录]
    [店铺名]  ●未登录        [登录]
    [店铺名]  ●等待登录…      [我已完成]
    [店铺名]  ●已登录·无待处理  [登录]

渠道标题行还有 **「登录全部未登录的店」**（串行，一次开一家 —— 紫鸟是本地浏览器，并发会互抢焦点）。

#### 巡逻页的两条信息设计（v0.8.0）

**每个平台块可以单独收起。** 亚马逊、TikTok Shop、沃尔玛、飞书邮箱各是一个块，标题左侧的 ▾ / ▸
可以单独收起 —— 几块列表加起来几十家店时，收起不想看的那几块才能一眼看到自己要管的。
收起状态存 localStorage，刷新页面后仍然保持。

**「N 个平台」与「M 家店」是两个口径，这里刻意区分开：**

| 位置 | 说法 | 实测数字 | 含义 |
|---|---|---|---|
| 最上面那条汇总 | 「另有 **21** 个平台（58 家店）不会被巡逻」 | 21 / 58 | **没有任何已启用渠道**会巡逻的平台 |
| 每个渠道块内 | 「本渠道不巡逻的另有 **23** 个平台（64 家店）」 | 23 / 64 | 只是**不是这个渠道**的店 |

为什么必须分开：**每个渠道的 skipped 里都包含被别的渠道巡逻着的店。** 亚马逊渠道的 skipped
里有 TikTok 的店，但那些店是被 TikTok 渠道巡逻的 —— 把 23 说成「不会被巡逻」就是错的。
所以全局那个数是从「全量平台 − 所有启用渠道 items 的平台并集」算出来的，
渠道块内的那个数措辞也刻意写成「本渠道不巡逻」。

这条口径算错过的代价很具体：数字看着对（都是十几个平台），但语义完全不同，
运营会以为 TikTok 也没接。`assets/js/platform-summary.js` 就是为这两个口径单独抽出来的纯函数模块，
`test/platform-summary.test.js` 用「两个数必须不相等」的用例把它们钉住。

#### 「登录」按钮**不是**自动登录

它的职责是：**把浏览器开到登录页摆好，然后停下来等人。**

**插件绝不代替人完成登录** —— 不点登录按钮、不填账号密码、不填验证码、不处理滑块。
（唯一的例外是 v0.12.0 的 TEMU：它会顺手把登录页**切到「手机号登录」那个 tab** —— 只切 tab，
不填任何内容、不点登录、不碰验证码。见「第六个渠道」那一节。）
两条理由：

1. **登录挑战的类型是不固定的。** 实测两次真实登录遇到两种完全不同的挑战：
   - `Tiktok-FUSOU-客服主号` → 滑块验证码「点击选中两个相同形状的物体」
   - `Tiktok-FUSOU-客服KX` → 6 位**邮箱验证码**（发到 `cs@jinmukeji.com`，无滑块）

   类型不可预测，插件没法先写好一套流程。
2. **验证码本来就发到人手上**，插件也拿不到；而代填账号密码等于绕过平台风控，
   一旦被判定为异常登录，责任说不清。

所以流程是：**你点「登录」→ 插件把窗口开好并停在登录页 → 你在窗口里过验证 → 插件自动探测到已登录。**
插件在后台每 3 秒探测一次；也可以点「我已完成」手动触发一次探测（是**真的探测**，不是盲信）。

#### 「登录成功」和「有活干」是两件事

实测 `Tiktok-FUSOU-客服KX`：**登录成功，但收件箱 0 条待处理会话**（只有 16 条已关闭历史）。
所以状态点会单独显示 **「已登录·无待处理」** —— 否则「登录成功却出不了草稿」会被误读成漏扫或坏了。

#### 巡逻遇到未登录的店：跳过它，不失败

点「巡逻」时，未登录的店会被**跳过**并在结果里写明：

> 未登录，请先点「登录」

它**不计入失败**（`sourcesFailed` 不动、`errors` 不动），而是进单独的 `sourcesSkippedAuth`；
进度条照常前进。已登录的店正常出草稿 —— **一次巡逻不会因为某家没登录就全废**。

（跳过的判据是适配器自己的能力探测 `typeof adapter.checkLogin === 'function'`，
不是平台白名单 —— 飞书邮箱渠道没有「登录」这回事，完全不受影响。）

#### 几个刻意的取舍

| 取舍 | 为什么 |
|---|---|
| 登录态**只放内存、不落盘** | 登录态本来就会过期；落盘成「永久登录」会出现「文件写着已登录、窗口其实停在登录页」 |
| 探测只读 URL，不读 DOM | 登录页与已登录页都可能还在渲染；用 DOM 判会把「还在加载」说成「没登录」 |
| 接口没给登录态时画灰点「未探测登录态」 | 不猜成已登录也不猜成未登录 —— 编一个状态比空着更误导 |
| 未登录时**不禁用**巡逻按钮 | 禁用像功能坏了；改成 banner 说明「会跳过它们，不算失败」 |

### 校准过 ≠ 万无一失

适配器上的 `verified: true` 与 `calibrationNote`（`/cs/api/health` 的 `channelCalibration` 里可见）
写明了边界，仍然**没有被覆盖**的是：

- 只在一家 **US 店**上校准，跨境主站 `seller.tiktokshopglobalselling.com` 的 /chat 未验证；
- 「未回复 / 未读」目前靠**行文本**判定，没有接平台自身的筛选控件；
- 发图/附件、快捷回复、转交等交互未涉及；
- **沃尔玛已校准，但列表容器没有可依赖的选择器**：它是一串 CSR 哈希类名（`Hiyc8`），随构建变，
  所以列表脚本直接找行（`.message.p-16`）而**不依赖容器**；系统通知类消息目前与买家消息一样
  按「非我方」处理（见「第四个渠道」的「尚未覆盖」）。

选择器仍保留多套兜底数组，全部落空时返回 `{ok:false, reason, tried}` 并带上**试过的选择器原文**，
绝不静默返回 0 条。控制台的「校准模式」**仍未实现**（Phase 3b 计划项），但现在不再需要它。

### 第二个渠道：飞书邮箱（v0.4.0）

亚马逊那条线看的是店铺站内信；平台通知、供应商、物流、货代的往来全在**邮箱**里 ——
那才是「漏回一封就出事」的地方。所以巡逻现在有两个渠道，界面上分块列出、各自勾选：

| | 亚马逊店铺 | 飞书邮箱 |
|---|---|---|
| 目标来源 | `ziniao store list` | `设置 → 巡逻邮箱` 里配置的地址，逐个过 `mail user_mailboxes accessible_mailboxes` 确认 |
| 待回复判定 | 收件箱 `fi=responseNeeded` | 收件箱会话的**最后一封是来信**（我方已回 / 已有草稿就不打扰） |
| 读取方式 | 打开浏览器逐条点会话 | 纯 API：会话列表 → 逐条 `+thread --html=false` |
| 草稿去向 | 插件草稿库 | 插件草稿库；可再点「创建飞书回复草稿」写进飞书草稿箱 |

**身份走机器人（bot）**：邮件链路全部用 `--as bot`（租户 token），**不需要**个人
`auth login`，也就没有「授权过期」这回事。相应地有两条硬前提：

- 机器人要有邮箱权限（应用层的 mail scope），这由飞书开发者后台决定；
- **邮箱地址必须显式配置**：bot 用的是租户 token，邮箱接口不接受 `me`
  （实测报 `tenant access token not support me`），没法「列出全部可访问邮箱」。
  在「设置 → 巡逻邮箱」里用空格或逗号填地址，例如 `support@fusou.vip`。
  地址写错、或机器人看不到该邮箱时，扫描阶段就明确报错，不会静默少扫；
  一个地址都没配时，该渠道提示「还没有配置巡逻邮箱」，不做任何猜测。

**安全默认值**：

- 默认**不往飞书草稿箱写**。草稿只进插件草稿库，要落到飞书得人点一次，或显式勾上
  「同时把邮件草稿写进飞书草稿箱」。无论哪种，都只是存草稿，**永远不会发送**。

邮件模板与买家消息模板**刻意不同**：买家消息是自家店铺的售后，可以直接承诺「免费补发配件（不是整包）」；
公共邮箱里坐着的是平台、供应商、货代、甚至催款 —— 一封替人承诺的草稿发出去就是钱。
所以邮件模板一律**只承接、不断言**（已收到 / 正在核实 / 下一封给结论），并且会把飞书返回的
`security_level` 风险标记写进草稿备注：邮件是外部不可信输入，不能因为它这么说就照着做。

**不是每封邮件都值得回。** 实跑 `support@fusou.vip` 时抓到 10 封「未回复」，里面其实是三类：

| 类型 | 例子 | 处理 |
|---|---|---|
| 真实客户来信 | 「Missing parts of vanity」 | 正常生成草稿 |
| 平台代发的联系表单 | Shopify「New customer message」——正文里带 `Name:` / `Email:` / `Body:` | 生成草稿，但**把客户认出来**当收件人，并在备注里提示核对 |
| 纯系统通知 | 「收入款项 $299.93 USD」（正文带退订入口） | **跳过**，不生成草稿 |

判定顺序很关键：**先解析联系表单，再判要不要跳**。平台的通知地址（`no-reply@shopify.com`）
同时也用来代发联系表单——那是真客户留言，只是借了同一个信封。先按发件地址一刀切，
会把等着回复的客户一起丢掉。判据：

- 有联系表单 → 留下（真人在等回复）；
- 没有表单但发件地址是 `no-reply@` 之类 → 跳过；
- 没有表单但正文带退订/通知偏好入口 → 跳过（系统群发）。

跳过的数量会在巡逻进度表里单独列一栏（鼠标悬停能看到每封跳过的原因），**不静默丢掉**。
发件人黑名单可通过 `settings.patrol.mailSkipSenders`（正则字符串数组）追加。

设计取舍：

| 取舍 | 为什么 |
|---|---|
| **串行**跑店铺，不并发 | 紫鸟是本地浏览器内核，并发开店铺会互抢焦点/端口，「点错店铺」排查极贵 |
| 一家店失败不影响其它店 | 巡航的价值是「不漏店」，不是「一次全成功」；失败原因记在这家店的结果里 |
| **不接 LLM**，模板化生成 | 一次跑几十家店，模板能保证同类问题同类答复；模型措辞反而增加复核成本 |
| 草稿存插件、不塞进亚马逊输入框 | 批量留几十个未发送的输入框是事故；要填必须人工点单条草稿的「填入亚马逊回复框」 |
| 同 `caseId` 只留一条草稿 | 一天跑多次不会堆出几十份一模一样的草稿；**去重键不含店铺**，因为同一个亚马逊账号在紫鸟里常登记成多条（管理员/客服各一条），它们看到的是同一批会话 |
| 读到空会话要重读 | `.case-message-view` 是乐观渲染的空壳，消息体之后才到；不等它就会拿到「没有消息」的会话，买家诉求全丢 |

**为什么永远不会误发**：巡逻链路上不存在发送动作。Amazon 剧本里 `submit.verified` 永久为
`false`、`submit.never` 为 `true`、`submit.selector` 为空字符串，并且有测试断言
（`test/amazon.test.js`）整条链路里不出现任何发送按钮。人工点「填入亚马逊回复框」时，
服务端只会点「填写留言」并往输入框写文本，写完就停。

### 草稿是怎么生成的

`lib/reply.js` 是纯函数，零 I/O、零依赖，可单独断言：

- **判意图**：`replacement / refund / shipping / return / cancel / invoice / acknowledge / inquiry`，按优先级匹配（先判换货再判退款，因为 "damaged, want a replacement or refund" 应该落到更具体的换货）；同时命中多个会标 `needsHuman`。
  **买家最后一条消息优先，亚马逊系统主题只当兜底** —— 主题描述的是*最初*的诉求，买家后来改口是常态。
  实跑踩过：主题写着 "Request a replacement item"，而买家已经回了两遍 "no thank you i would jus like the refund"，
  按主题判就会生成一封「我们很乐意给你补件」的草稿，跟买家刚说过的话正好相反。草稿里的
  `intentSource`（`message` / `subject` / `none`）会告诉复核的人这封草稿的依据是什么。
- **抠订单号**：只认亚马逊的 `3-7-7` 形式。
- **抠收货地址**：只认「门牌号 + 街道类型词 + 州缩写 + 邮编」硬证据。买家一条消息里同时给旧地址和新地址是常态，所以返回**数组**，草稿把候选全列出来让买家确认，而不是替买家猜。
- **推品牌**：从 `Amazon-Cozynome-管理员` 推出 `Cozynome` 做署名。
- **判语言**：按虚词命中数（≥2 个不同词）判德语/西语/法语/意语，只在草稿备注里提示「买家可能是德语，草稿是英文」。
- **标风险**：非英语买家、缺少订单号、意图歧义、走了退款模板（"已处理退款"是断言句）都会写进 `notes`，在列表里标「需确认」。

草稿正文里**不会出现邮箱和链接** —— 亚马逊站内信会把它们拦掉，有测试断言。

### 话术口径（v0.14.0）：不索要订单号，损坏走「补发配件」

两条全渠道统一的口径，五个模板族（Amazon / TikTok / 沃尔玛 / SHEIN / TEMU）与飞书邮件都适用：

| 场景 | 口径 | 为什么 |
|---|---|---|
| 任何意图 | **不向买家索要订单号** | 会话本身就带着这一单（草稿摘要里也有单号），让买家再报一遍只是多一轮往返。识别出来的单号照旧进 `summary` / 备注留痕，但不写进正文 |
| 损坏 / 补件（`replacement`） | **直接要照片 + 承诺免费补发配件** | 模板里写死「`part only, not the whole set`」—— 补的是那一个配件，不是整包，也不要求买家寄回或付钱 |

- 这是模板族里**唯一一处主动承诺**：`refund` / `return` / `invoice` 仍然「只承接、不断言」。
- 缺订单号时的内部备注（「发送前请补上」）保留 —— 那是给复核的人看的，不是发给买家的话术。
- 回归锁：每个渠道的 `test/reply-*.test.js` 都断言正文里不出现 order number，损坏用例断言
  `photo` / `free of charge` / `part only, not the whole set` 三件事；邮件侧在 `test/reply-mail.test.js`。

## 安装

插件是标准 npm 包 + DSH bundle patch，**没有任何 `@deepseek-ai/*` 运行时依赖**，也不需要 `config:` 配置，所以同一个包在任何 DSH 实例上都能原样安装。

### 方式一：GUI（最省事）

DSH → 侧边栏 **Plugins** → 安装外部 bundle → 选择本包目录或 tarball → 启用。

### 方式二：`plugin_manager` 工具 / `dsh plugin`

```sh
# 普通 profile（web、自建 profile 等）
dsh plugin --profile <profile> add /absolute/path/to/dsh-customer-service-plugin-0.2.0.tgz

# desktop 这类由 Electron 独占的 profile，用它自带的 CLI
"/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh" \
  plugin --profile desktop add /absolute/path/to/dsh-customer-service-plugin-0.2.0.tgz
```

### 方式三：本地开发（改完即生效）

```sh
dsh plugin --profile <profile> add link:/absolute/path/to/packages/dsh-customer-service-plugin
```

安装后**重启或重载 DSH**（profile 的 `patchReload` 若不是 `live` 就需要重启）。

### 打包分发

```sh
cd packages/dsh-customer-service-plugin
npm pack            # 产出 dsh-customer-service-plugin-0.2.0.tgz
```

## 配置

**不需要改任何 YAML。** 全部设置保存在插件自己的 `settings.json` 里，由控制台界面点击修改：

| 项 | 说明 |
|---|---|
| 数据目录 | 计划、队列、草稿、剧本、审计的存放位置 |
| 紫鸟CLI 路径 | 自动探测不到时手动指定 |
| 飞书CLI 路径 | 同上 |
| **CLI 附加参数** | 前置到该 CLI 的每次调用之前。飞书换身份就靠它：`--profile <profile 名>` |
| 时区 | 生成窗口按此时区解释，默认 `Asia/Shanghai` |

### 用别的飞书身份（profile）

飞书的「身份」不是换二进制，而是给 lark-cli 加 `--profile`：

```json
{
  "cliPaths": { "lark": "/opt/homebrew/bin/lark-cli" },
  "cliArgs": { "lark": ["--profile", "example-lark-profile"] }
}
```

参数**必须前置**：实测 `lark-cli --profile X --version` 合法，而 `lark-cli --version --profile X`
会失败。`settings.json` 里写成数组，或在界面上按空格分隔手输（支持引号包住带空格的片段）。

> 注意：改了宿主半代码之后，**在重启 DSH 之前不要点「保存设置」** —— 运行中的旧模块
> 不认识 `cliArgs`，一点保存就会把它从文件里抹掉。

默认位置与优先级：

```
settings.json :  $DSH_CS_DIR                       （若设置）
                 否则 <DSH_HOME 或 ~/.dsh>/customer-service/<DSH_PROFILE 或 default>/

数据目录      :  settings.json 里的 dataDir         （若设置）
                 否则与 settings.json 同目录
```

环境变量覆盖：`DSH_CS_DIR`、`DSH_CS_PREFIX`（控制台路由前缀，默认 `/cs`）、`DSH_CS_DEBUG=1`、
`ZINIAO_CLI_PATH`、`LARK_CLI_PATH`。

**设置文件位置固定、`dataDir` 只决定大块运行数据放哪** —— 这样切换数据目录不会留下两份互相矛盾的配置。

```
/cs/#/work/patrol   工作台 · 巡逻   一键巡逻全部 Amazon 店铺 + 草稿库（看/改/复制/填入回复框）

/cs/#/work/stats    工作台 · 统计   业务指标（工单）+ 运行指标（CLI / 体检）
/cs/#/settings      设置            体检四卡 + CLI 路径与附加参数 + 数据目录 + SLA / 审计保留
```

「设置」承载配置，「工作台」承载日常操作。飞书邮件同步、规则引擎、草稿生成落地后，
它们的数据会直接进队列，**统计页不用改**。

### 视觉与样式

界面只有一份样式表 `assets/app.css`，按「设计令牌 → 组件」两层组织，零构建、零依赖：

  `assets/index.html` 头部的引导脚本把它落到 `<html data-theme>` —— 排在样式表之前是为了暗色下不闪白。
- **可读性**：正文 / 次级文字 / 语义色（成功、警告、危险）按 11~12px 小字的 4.5:1 取值；输入框、下拉、
  开关另用一档更实的描边（`--cs-control-border`），保证控件边界看得清。
- **组件**：按钮（默认 / 主要 / 幽灵 / 危险 / xs / xl）、状态徽章（带色点）、滑杆式开关、
  表格（`.table-wrap` 圆角 + 窄屏横滑 + 首列钉住）、抽屉（`clip-path` + 超大投影当遮罩，不额外插 DOM）、
  空状态、轻提示、KPI 卡、分布条、纯 SVG 图表。
- **窄屏**：DSH 侧栏里的 iframe 只有 460px 左右，所以断点定在 700 / 640px：顶栏折行、表单单列、
  表格横向滚动且状态列 sticky、行内边距收紧。

### 每个渠道自己一枚「启用 / 停用」开关（v0.13.0）

巡逻页每个平台块的右端（「上次扫描」左边）有一枚滑杆开关，**每个渠道各管各的**：

    ▾  TikTok Shop（6）  ●6 家未登录   [开关] 已启用   上次扫描 10-12 14:10   [登录全部未登录的店] [仅刷新列表] [重新扫描]
    ▾  SHEIN（15）      ●15 家未登录  [开关] 已停用   上次扫描 10-12 14:10                      [仅刷新列表] [重新扫描]
    ▾  飞书邮箱（未启用）              [开关] 已停用   上次扫描 10-12 14:10                      [仅刷新列表] [重新扫描]

- 关掉之后这个渠道**立即**不参与巡逻与「重新扫描」，这块里的按钮一并变灰；扫描接口回报
  `disabled: true`（**不是错误**），并给出一句「为什么没在跑」。
- 真值写在 `settings.channelEnabled[渠道 id]` 里，是一张**稀疏表**：只存你真的动过的渠道。
  没写进表的渠道走适配器自己声明的默认值（店铺类渠道默认开、飞书邮箱默认关）——
  把默认值也写进文件的话，将来改默认值就对老配置失效了，「没设过」和「显式设成默认」也会被抹平。
- 飞书邮箱那个老开关（`settings.mailEnabled`）**仍然有效**，它与这里的开关指向同一处真值：
  两个入口（设置页那个复选框 / 巡逻页这一行）写哪个都行，读出来的永远一致。
- 「没在跑」有**两种原因**，界面上分开说：开关本身关着 = 「已停用」；而**紫鸟CLI / 飞书CLI 被禁用**时
  渠道开关其实还开着 —— 这时开关仍画成「已启用」，提示里写明「紫鸟CLI 已在设置里禁用」。
  把这两种混成一种，人会对着一个从没关过的开关反复点。
- 前端靠 `/meta` 的能力位 `patrol.channelSwitch` 认旧后端：旧后端的 `/patrol` 里没有
  `channels[*].switchOn`，开关画出来也是点了没反应，所以**干脆不画**，顶部直接提示「请重启 DSH」。

`settings.channelEnabled` 的形状（省事起见也可以手写进 settings.json）：

```json
{
  "channelEnabled": { "temu": false, "lark-mail": true }
}
```

字段名注意一处**刻意的不一致**：`/patrol` 里每个渠道报两个字段 ——
`enabled`（现在跑不跑 = 渠道开关 ∧ CLI 开关）与 `switchOn`（这枚开关本身）；
而 `/health` 的 `autoPatrol.channels[*].channelEnabled` 是**第一个**的意思。
同名字段在两个 payload 里意思不同是最容易写出 bug 的坑，所以这里换了名字。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/cs/api/health` | 体检（CLI、宿主能力、数据与存储） |
| GET | `/cs/api/meta` | 维度枚举与状态跃迁表（UI 的下拉与按钮都从这里取） |
| GET/POST | `/cs/api/settings` | 读写设置（POST 需要 `x-cs-token`） |
| POST | `/cs/api/detect` | 强制重新体检 |
| GET | `/cs/api/stats?days=7\|14\|30` | 统计（业务组 + 运行组，**口径全在服务端**） |
| GET | `/cs/api/activity` | 活动审计分页（脱敏后的元数据） |
| GET/POST | `/cs/api/queue` | 工单列表（带筛选与计数）/ 新建 |
| GET/PATCH | `/cs/api/queue/:id` | 单条详情 / 改状态、改派、加备注（带 `rev` 乐观锁） |
| GET | `/cs/api/patrol` | 巡逻状态：进行中/最近一次、每店明细、进度、账号下的 Amazon 店铺 |
| POST | `/cs/api/patrol` | **一键巡逻**入口（202 立即返回，后台继续跑） |
| POST | `/cs/api/patrol/stop` | 请求停止：跑完当前这家店就收工 |
| GET | `/cs/api/patrol/stores` | 店铺扫描结果（带 60 秒缓存，`?refresh=1` 强刷） |
| POST | `/cs/api/patrol/scan` | **手动扫描可用目标**：跳过缓存重跑，返回每个渠道的新增/移除差异（`{channels:[...]}` 可只扫指定渠道） |
| GET | `/cs/api/drafts` | 草稿列表（按店铺/意图/状态/需人工/关键字筛，自动按紧急度排序） |
| GET/PATCH | `/cs/api/drafts/:id` | 单条草稿详情 / 改正文、改状态（带 `rev` 乐观锁） |
| POST | `/cs/api/drafts/:id/fill` | **人工触发**：把草稿文本填进**该草稿所属平台**的回复框（不发送；按 platform 分派到 Amazon / TikTok / 沃尔玛 适配器） |
| POST | `/cs/api/drafts/:id/mail-draft` | **人工触发**：在飞书里建一封回复草稿（不发送，仅飞书邮件草稿） |

写操作一律校验 `x-cs-token`；状态跃迁非法返回 400 并带上允许的下一状态，乐观锁冲突返回 409。

### 改完宿主半，先跑一次「真宿主激活」冒烟测试（v0.8.0 起）

`npm test` 全绿**不等于**插件能在真实宿主里跑起来。这两件事之间有个真实的坑，值得单独记住：

**单测里的 ctx 是普通对象，真实的 Cordis ctx 是 Proxy。** 给一个没有用 `ctx.provide`
声明过的属性赋值：

```js
ctx.pluginRuntime = runtime;   // 单测：通过。真实宿主：抛异常
```

而 `apply()` 是插件的**激活函数** —— 在这里抛出去，整个插件就挂不上：控制台路由不注册、
**界面一片白**，宿主只留一行 warning：

```
dsh: warning: 1 entry did not activate
customer-service: Error: cannot set property "pluginRuntime" without provide
```

这个坑真实发生过一次：365 个单测全绿，界面上却是白屏，排查了很久。

所以有两条防线：

**1. 单测里有一条严格替身（`test/plugin.test.js` 的 `strictContext()`）。**
它模仿真实 Cordis：任何未声明的属性赋值都抛。普通假 ctx 会放过的写法，它当场拦下。

**2. 一个真宿主冒烟测试：`npm run smoke`。**
它建一个**一次性最小 profile**（base + web-app + 本插件），用 `dsh` CLI 在真 Cordis 里启动，
请求 `/cs/api/meta`，能返回 200 才算过；失败会把启动日志原样打出来。

```sh
npm run smoke
# ✓ 插件在真实宿主里激活成功  version=0.12.0 channels=["mail","tiktok","walmart","shein","temu","amazon"]
```

改动 `lib/index.js`、`lib/client.js`、`package.json` 或 `cordis.patch.yml` 之后，
**提交前跑一次 `npm run smoke`** —— 它覆盖的正是「宿主到底怎么加载你」这件事，
而这是单测结构上覆盖不到的。

### 改代码前必须知道的运维事实

- **`assets/` 每次请求现读**：改 HTML/CSS/JS 刷新页面就生效，不用重启。
- **`lib/*.js`（宿主半）必须重启 DSH**，这是**唯一可靠手段**。Node 按「解析后的真实路径」
  缓存模块：路径不变就永远拿旧的；路径变了但那个路径以前 import 过，还是会拿到更早的实例。
  已实测**全部无效**：`plugin_manager` 的 disable/enable、重装同版本号、换安装协议
  （`link:` ↔ tarball，试了两次，只有一次碰巧生效且不可复现）。
- **由此会产生「前端新、后端旧」的错配**：资源是现读的、模块是缓存的。
  控制台会主动探测并在顶部给出「请重启 DSH」的提示；命令行用
  `node scripts/check-plugin.mjs` 判断（它会分别检查前端模块与新接口）。
- **重装同一个版本号不会更新副本**：pnpm 见版本号未变就跳过解析。改完要么升版本号，
  要么 `dsh plugin --profile <p> remove <pkg>` 再 `add`。

### 为什么保持零构建

Host 半就是 `lib/index.js`，Client 半就是手写的 `lib/client.js`
（宿主 `window.__ModuleLoader__` 的懒加载 CJS 工厂格式，和 DSH 自带客户端插件同形）。
没有 TypeScript、没有打包器、没有 `lib/types/`。

### 为什么不用 `defineTool` / `Service` / `Schemastery`

`@deepseek-ai/dsh-tools` 的 `defineTool` 只是把 DSL 编译成 JSON Schema，而
`ctx.tools.register` 只校验 `{name, description, parameters, output:{schema, render}}`。
所以这里用普通对象定义工具，省掉依赖，也顺带绕开了 peer 版本校验 —— 这是「别的 DSH 也能装」的前提。
同理：服务用 `ctx.provide`，配置走自己的 `settings.json`。

## 重新巡逻时，什么会被覆盖、什么不会

先澄清一个常见误解：**重新巡逻不会重复造草稿。** 草稿按 `platform:case:<caseId>` 去重，
再跑一遍只会「更新」已有草稿，不会新增；数量增加通常是真的来了新消息。
（实跑验证：第二次巡逻 `draftsCreated: 1, draftsUpdated: 9` —— 新增那条确实是新邮件。）

真正需要小心的是**覆盖**。规则：

| 草稿状态 | 重新巡逻时 |
|---|---|
| 没人动过 | 正文照常刷新（模板改进了，老草稿也跟着更新） |
| 人工改过正文 / 批过 / 填进过回复框 | **正文原样保留**，只刷新到期时间这类会变的元数据，并在时间线记一条「保留人工版本」 |

计数上也分开：`draftsCreated` / `draftsUpdated` / `draftsPreserved`，界面上不会把「保留」混进「更新」。

### 回复默认直接填入紫鸟浏览器（不再是开关）

巡逻读到一条会话生成草稿后，会顺手把草稿填进**当前已经打开**的那条会话的回复框，
并把草稿标成 filled。**只填不发送**，落点就是紫鸟CLI 打开的那个可见浏览器窗口 ——
核对无误后你自己点发送。

- **默认开启、界面上没有开关、settings.json 里也没有这个键**：草稿的归宿就是回复框，
  这件事不需要人来开。只有直接调 POST /patrol 并显式传 autoFillAmazon: false 才能临时关掉
  （留给测试与排障）。
- **无头模式已移除**：store open 永远不加 --headless。窗口不可见的时候把文本填进回复框
  没有任何意义 —— 没人看得到，也没法核对。
- 不额外导航：巡逻读会话时页面已经在那条会话上了，直接输入即可。「填写留言」那个按钮是
  **有就点一下、没有就算了** —— 新 NGS 消息中心里回复框常常默认就展开着，此时页面上一个
  kat-button 都没有；把「点按钮」当成必须成功的一步，就会明明输入框在眼前却报
  ELEMENT_NOT_FOUND（v0.5.0 修的就是这个）。判据永远是「输入框在不在」。
- 填入的是**草稿库里的正文**，不是刚生成的那一份 —— 否则人工改过的草稿会出现「库里新版、浏览器里填的旧版」。
- 标成 filled 会同时让这条草稿进入上面的「人工动过」保护名单：正文正躺在真实浏览器输入框里，
  下次巡逻再覆盖只会让两边对不上。
- 代价要知道：跑一遍 8 家店会在紫鸟浏览器里留下十几到几十个未发送的输入框。
  另外「跑完关闭店铺」会把还没发送的回复一起关掉，所以它默认关闭。

### 两个踩过的坑（都会让「默认回填」看起来完全没生效）

1. **打开会话不能用紫鸟CLI 的 page click**。2026-10-08 实测：它会打印「鼠标指令：已发送」，
   却「DOM 点击事件：未观察到」，于是每一条会话都报 ELEMENT_NOT_INTERACTABLE —— 而同一时刻
   用 elementFromPoint 检查，那一行就在点上、pointer-events 是 auto、可见不透明，元素本身
   完全正常；换成脚本里的 el.click()，同一条会话一次就打开。所以列表行与「填写留言」按钮
   都改走「page exec + 脚本点击」（顺带先 scrollIntoView：列表可滚动，顶部还有一条悬浮 KPI
   条，行落在可视区外时鼠标坐标根本不在页面上）。
2. **「填写留言」按钮不是必然存在的**。新 NGS 消息中心里回复框常常默认就展开着，此时页面上
   一个 kat-button 都没有。把「点按钮」当成必须成功的一步，就会明明输入框在眼前却报
   ELEMENT_NOT_FOUND。判据永远是「输入框在不在」。

### 这次新跑出来的草稿会标色

草稿库里，**最近一次巡逻新生成的**那些草稿会整行带一种颜色：左边一条色线 + 淡底色，
状态旁边多一个「本次新增」小徽章，列表顶上还有一行同色图例写明这批新增了多少条。

- 判断口径是「草稿的 runId == 最近一次巡逻的 id」：只有这一次真的**新建**的算，
  更早那几批不算，人工建的也不算。
- **每次重新巡逻换一种颜色**（6 色，按 run id 稳定取色），所以连着跑两次能一眼认出
  哪批是哪批；同一个 run 不论刷新多少次、怎么筛选，颜色都不会跳。
- 重启 DSH 也还在：内存里没有 run 时从 run/patrol-last.json 兜底读最近一次巡逻 ——
  「这批是刚跑出来的」恰恰是重启之后最想知道的事。

### 「丢弃」和「删除」不是一回事

草稿上有两个看起来都在处理掉它的动作，差别是**能不能反悔**：

| 动作 | 做了什么 | 能反悔吗 |
|---|---|---|
| 丢弃 | 状态改成 discarded，记录和正文都还在 | 能，把状态改回去就行 |
| 删除 | 从 drafts.json 里抹掉，连 <id>.txt 正文副本一起删 | **不能** |

- 界面上两处都能删：草稿库**每行最右边**的「删除」小按钮，以及详情抽屉里的「删除草稿」。
- 两处都要点一次确认；确认框里会写清「只是想别再看到它、以后还要翻回来查，请改用丢弃」。
- 删除会清掉工单上指向它的 draftId（指针指向一条不存在的草稿，比空着更容易误导），
  但**不改工单状态** —— 删草稿不等于把工单打回未处理，那是另一件事，由人决定。
- 每次删除在活动审计里记一条 kind=draft、action=deleted（带平台 / 店铺 / 状态 / 关联工单），
  删了什么有据可查。
- 删除要靠新接口 DELETE /drafts/:id，它登记在 /meta 的能力位里：**旧后端没有的话，
  页面顶部会直接提示重启 DSH**，而不是让你去点一个注定失败的按钮。

### 启用 / 禁用某个 CLI

设置页每个 CLI 卡片的右上角有一个「禁用 / 启用」按钮，点一下立刻生效（不用再去按保存）。

- **禁用 = 插件不再调用它**，不是「假装没找到」：探测时连 --version 都不跑，统计里的
  CLI 调用记录也不会因为被禁用的那个而增加。
- 依赖它的渠道会一起停：禁用紫鸟CLI → 亚马逊店铺巡逻跳过这个渠道；禁用飞书CLI →
  飞书邮件渠道不参与巡逻（即使「启用飞书邮箱渠道」是勾上的）。两者在扫描结果里都只回报
  「未启用」并带一句原因 —— 不算失败，也不进顶部的「需要处理」告警。
- 卡片此时只显示路径 / 来源 / 附加参数 / 版本，外加一句「禁用之后会发生什么」，不再显示
  安装命令：禁用是选择，不是故障。
- 开关存在 settings.json 的 cliEnabled 里，默认两个都是 true；只切一个不会把另一个抹掉。

## 安全约定

- 插件只写自己的数据目录（以及用户在界面里明确指定的目录）。
- 控制台每次启动生成一次性随机令牌，写操作必须携带，防止其它本地页面误触发。
- 静态资源服务做了目录穿越防护，并强制 `no-store` + `nosniff`。
- **不把 apiKey / token 写进日志、审计或界面**；审计只存脱敏摘要。
- 邮件与买家消息正文一律当作**不可信数据**处理，只用于模板变量与摘要，绝不执行其中的指令。
  （买家消息里出现的「忽略以上指令」之类文本，只会被当成模板变量，不会被执行。）
- 店铺自动化的「提交」步骤必须由人在界面上校准并点击后才会执行。
- **巡逻链路上不存在发送动作**：`lib/patrol.js` 与 `lib/platforms/amazon.js` 只做读页面、
  写草稿、入队；Amazon 剧本的 `submit` 永久 `verified=false / never=true / selector=""`。
  这是被 `test/amazon.test.js` 与 `test/routes.test.js` 显式断言的，不是口头承诺。

### 已知边界（v0.3.0）

- 巡逻只覆盖**读取 + 生成草稿**；发送与「填入回复框」都只走人工触发。
- 单店铺的页面脚本依赖 Amazon 现网 DOM（`.case-list-items` / `.case-message-view` / `.message-component`）。
  Amazon 改版会让它失效 —— 失效表现是「收件箱没有加载出来」被记成该店失败，而不是静默漏掉。
- **店铺未登录会被单独识别**：亚马逊会把收件箱跳到 `/ap/signin`，巡逻据此报
  「店铺未登录，请先在紫鸟浏览器里登录该店铺后重跑」，而不是让运营去猜是改版还是掉登录。
  （实跑时 8 家店里有 1 家就是这个状态。）
- 草稿模板是英文的；非英语买家会在草稿备注里提示，需要人工按买家语言调整。
- `lib/*.js`（宿主半）改动**必须重启 DSH** 才生效，`assets/` 刷新页面即可。
- `lib/client.js`（浏览器半边）由 DSH 的客户端插件通道加载，不在 `assets/` 里，
  属于「改了要重载」的那一类。

### 客户端半边必须声明 `inject: ['slots']`（v0.3.1 修复）

早期版本写成 `inject = []` + `ctx.get('slots')`，后果是**侧边栏底部没有「客服」按钮，
而且不留任何痕迹**：浏览器端上下文里服务挂在 `ctx.slots` 上（DSH 自身有 92 处
`inject: ['slots']`），`ctx.get('slots')` 拿不到 → 旧代码「静默 return」→ 什么都不注册。
现在改成 `inject = ['slots']` + `ctx.slots`（保留 `ctx.get` 作兼容回退），并且拿不到时
会往控制台打一行明确错误 —— 这类失败最贵的不是修，而是它不说话。
